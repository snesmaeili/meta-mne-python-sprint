Epochs that don’t all last the same

A walk through the changeset: which code paths exist now, what every method does when durations vary, and what the validation against 24 real recordings actually showed.

One class, two paths

The change adds no new class. Epochs already takes tmin and tmax; those may now be arrays with one entry per event. Everything downstream turns on a single boolean, _variable_duration, decided once at construction.

Bounds that are arrays but carry no actual variation collapse back to scalars. That matters more than it sounds: it means passing np.full(n, -0.2) behaves exactly like passing -0.2, so nothing existing changes behaviour by accident.

What each method does now

Before this, an audit of the public API on variable-duration epochs found thirteen methods failing with errors like 'list' object has no attribute 'shape', and shift_time quietly returning epochs it had not shifted. Neither is a reasonable thing to hand a user.

Every public method now falls into one of three groups. The split is not arbitrary: it follows what the operation means, not how hard it was to fix.

The first version of this changeset had every method in the third and fourth groups warn and run on a padded copy, which is the migration path suggested in the issue. Measuring it changed the design. average() on realistic durations returns a result that is 44% NaN — one short epoch takes out a whole time point — while nave still reports the full count. And compute_tfr() padded before transforming, which is the reverse of the order this work argues for, on a path no test covered.

So only inspection falls back now. Anything numeric either works on the ragged data or says why it will not. The distinction inside the two raising groups matters for the reader: a reduction needs a decision from you, whereas filter is simply per-trial work nobody has written yet.

There is no shared time axis, so times says so

epochs.times raises when durations vary. The alternative was to return the union of all epochs, which is what an earlier version did — but that leaves len(epochs.times) == data.shape[-1] false while looking perfectly ordinary, and that is how silent errors get made downstream.

get_times(i) gives one epoch’s real axis; as_fixed().times gives the padded common one. Both are explicit about which you asked for.

What as_fixed() costs

It pads every epoch to span the union window and returns the padded copy together with the number of epochs still carrying real data at each sample. That second return value is the point of the method.

Why the count is returned rather than dropped. This is the objection raised against padding on the earlier PR — that the noise level becomes time-dependent and nave stops describing it. Returning the per-sample count makes the shortfall visible instead of hiding it behind one number.

How it was checked

What is deliberately not done

This is the first of several changes, not the whole feature. The order is chosen so each step is small enough to review on its own.

  1. Container, as_fixed(), the dispatch above, and the duration-preserving operations natively — __getitem__, pick, drop, shift_time. This changeset.
  2. Per-trial operations natively: filter, apply_baseline, crop, decimate, resample. Currently raising.
  3. compute_tfr and compute_psd with a stated policy for the frequency grid.
  4. FIF reading and writing.
  5. What the reductions should do about a contributing count that varies over time.

Three things a reviewer may push on

Is raising from times the right call?

It refuses when durations vary. The alternative is to return the union of all epochs, which is what as_fixed() produces — convenient, but it leaves len(epochs.times) == data.shape[-1] false while looking entirely ordinary, and that is how quiet errors happen. The union is still reachable through as_fixed().times. Left open in the issue on purpose.

Arrays on an existing argument

Passing tmax as an array changes what the object is. The counter is that it is opt-in at construction, and a separate class would mean duplicating sixty-odd methods.

Padding under the reductions

Falling back to as_fixed() for average is convenient and also reintroduces exactly the problem the earlier PR stalled on. The warning says so, and the per-sample count is returned, but whether that is enough is a real question.
